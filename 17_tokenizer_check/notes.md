# 17｜训练与检验 tokenizer

## 核心概念

词表大小是可用 token ID 种类数，不是上下文长度。中文、英文、代码和数字都应做编码/解码、压缩率及异常切分测试。

## 观察一个例子

32K tokenizer 通常表示约 32768 个 token ID；一次可读多少 token 由模型上下文配置决定。用中文、英文、数字混合句各取十条，编码后再解码，检查是否还原。随后统计每类每百字需要多少 token；如果中文数字被切得异常碎，就回头查词表样本。

## 技术细节与实践流程

### 技术机制

训练 tokenizer 时先确定算法、规范化方式、字节覆盖和特殊 token，再从训练数据中抽取有代表性的样本学习词表。32K 在本案例中是 32768 个 ID，与模型 1024 的序列长度独立。固定 tokenizer 后统计每类文本的 token 数、回编码误差、未知片段及长序列比例，评估编码是否适合目标分布。

### 实践步骤

demo 用最长匹配演示子词编码，并不是 BPE 训练器。正式验收应包含中文、英文、数字、代码、标点和混合文本，并比较 16K/32K 在同一份样本上的长度与成本。特殊 ID 要写入配置并检查 `< vocab_size`；用 uint16 存储时还应确认所有 ID 均落在 0–65535 范围。

### 检查与常见错误

更少 token 不代表一定更好的语言能力：词表增大也会增加 embedding 与输出层开销。抽样回编码通过不能证明所有网页都无乱码；同时检查全量 ID 范围和编码失败数。切分规则、特殊 token 或规范化改变后，需重新计数并生成匹配的训练产物。

## 自问自答

**问：词表翻倍会自动让上下文翻倍吗？**

答：不会；两者是独立配置。
